处置一起挖矿病毒入侵

Posted 2026-10-05 ‐ 6 min read

平时跑实验喜欢用btop看负载，从前几天开始发现btop经常是这么个画风：

注意到什么了？CPU负载100%，但是进程列表里什么异常都没有。

第一反应：btop出bug了，CPU指示器是假的？

第二反应：服务器上另外有人在整虚拟机或容器相关的活，btop看不到？

第三反应：服务器中挖矿病毒了，病毒把自己隐藏了！

不敢猜，怕真查出来是挖矿，然后还得我来处理。

于是就屏蔽着挖矿猜想凑合过了两三天。这期间每看一眼btop都感觉不对劲，如果是有人在跑实验，这好像也太久了，如果是btop的bug，我有什么别的手段查负载呢？在/proc之类的哪里找？

但是偶然注意到进程列表里一个诡异的项目闪过，只有PID=443656，后面的项目全是空白。

$ sudo ls -A /proc/443656
CodeStore-1blc03e7aa518398  ins.sh.1878467  libpod_lock  libpod_rootless_lock_1001

看到这里我还在想，是什么进程把/proc/PID​里的东西都干没了，还当成tmpfs在用？ins.sh是什么安装脚本？但是怎么是空文件？这个libpod看着像是什么容器的什么锁文件，1001看着好像UID，我们的UID=1001是谁？好像是在研究容器啥的同学，CodeStore是vscode的什么临时文件？他确实有在用vscode。所以这是他在跑什么诡异容器，但是这个诡异容器把/proc/PID里的东西都干没了，还当成tmpfs在用？

还是再看看journalctl怎么说。

首先注意到了这个诡异的名字“tmuxinfoX”。再结合上面那些文件名，这我再不敢猜都不得不意识到了，恶意程序很常见的名字伪装手段。

其次看到“umount /proc/443656”，看来/proc/PID和mount有关？

接着看到“journalctl --vacuum-time=1s”。抹除日志，妥妥的恶意行为了。

$ mountpoint /proc/443656
/proc/443656 is a mountpoint
$ mount | grep 443656
tmpfs on /proc/443656 type tmpfs (rw,nosuid,nodev,inode64)

我说这还挺天才的吧，挂载个tmpfs就给自己隐藏了。

所以直接umount吗？不太敢直接碰/proc里的东西，怕打草惊蛇又让它用什么别的手段藏起来。有什么办法看到挂载点下的内容？一时不知道。

也许可以做个kmod进内核态探查一番，这应该就是内核态对抗吧，感觉是一些反病毒软件才会整的活，也许之后有必要研究一下。

换个思路，/proc​实际上是挂载了一个类型为proc的文件系统。

$ mount | grep proc
proc on /proc type proc (rw,nosuid,nodev,noexec,relatime)

所以只要换地方再挂一个proc就行？

$ mkdir ./proc
$ sudo mount -t proc proc ./proc
$ sudo ls ./proc/443656/
arch_status         cpuset             latency     ns             sched         syscall

$ cd ./proc/443656

接下来就好办了。要提取可执行文件样本，只要找/proc/PID/exe​。这是一个符号链接，但是作为一个合格的恶意程序怎么会忘记删除自己呢，所以readlink​指向的路径会是已删除的文件。但是没关系，直接cat是能读出来的。

$ sudo cat exe > ../../proc-443656

再用scp提取到我电脑上，您猜怎么着，直接被火绒给没收了。

这下看来是挖矿病毒没跑了。根据以往经验，挖矿病毒多半是通过弱密码爆破侵入进来。我们有四台服务器，两台旧的早期由一位经验丰富的管理员维护，大概都是强密码；我现在所用的服务器属于新的一批，这两台用户多，管理员比较缺乏经验，且我明确知道其上存在或存在过弱密码。我全部查了一遍，果然，另一台新的也中招了同款病毒，两台旧的都没有受影响。

查阅日志，发现确实有一个地址在持续进行ssh登录尝试，可能是网络内其他被感染的设备。由于早期日志被抹除，只发现该地址在一台服务器上成功登录，被登录的用户具有sudo权限，且其.bash_history被清空。

没有什么别的线索了，回去追查一下那个“tmuxinfoX.service”。

我以为我真该睡了，但是仔细看了好几遍，cat明明能正常读，ls的输出就是没有“tmuxinfoX.service”。这也太诡异了。

我以前处置过的挖矿病毒，有的会植入kmod​隐藏自己的/proc，还是在dmesg里留了有kmod安装信息才查出来（关键词“yayaya”）。也许这次也用了类似手段隐藏了一些东西，但是我dmesg和kernel-chktaint查下来没发现什么异常。一边在想还有什么手段可以探查内核态，一边下意识怀疑ls有问题。

注意到什么了？正常发行版安装的二进制程序应该基本都是“dynamically linked”吧，这个ls怎么是“statically linked”？

所以是ls被病毒替换了，自动把“tmuxinfoX.service”给隐藏了？那我系统里还剩多少东西是可信的？busybox你在吗？

$ busybox ls /usr/lib/systemd/system | grep tmux
tmuxinfo3035aa41.service
$ ls /usr/lib/systemd/system | grep tmux

幸好busybox看起来还好好的。这个ls提取下来依然是火绒没收。

得亏注意到，要不然还真让它潜伏起来了。既然动了系统文件，那就不能假定只动了一个系统文件，得来个全面扫描。有什么办法检查动了哪些文件吗？有的，debsums可以比对系统里哪些由deb包安装的文件被修改。

$ sudo apt install debsums
$ sudo debsums --changed

检查排除一些干扰项后剩下这些：

/usr/bin/dir
/usr/bin/ls
/usr/bin/chattr
/usr/bin/passwd
/usr/bin/uptime
/usr/bin/w
/usr/bin/systemctl
/bin/netstat

基本都是被换成了statically linked，但是chattr最奇怪：

$ cat /usr/bin/chattr
echo -e Usage: vmlinux1 [-pRVf] [-+=aAcCdDeijPsStTuF] [-v version] files...

此时我还没意识到这是啥意思，感觉像是某些奇妙的alias。

要把它们还原也容易，apt reinstall​就行。要找到它们属于哪个包，dpkg -S就行。

$ dpkg -S /usr/bin/dir /usr/bin/ls /usr/bin/chattr /usr/bin/passwd /usr/bin/uptime /usr/bin/w /usr/bin/systemctl /bin/netstat
coreutils: /usr/bin/dir
coreutils: /usr/bin/ls
e2fsprogs: /usr/bin/chattr
passwd: /usr/bin/passwd
procps: /usr/bin/uptime
procps: /usr/bin/w
systemd: /usr/bin/systemctl
net-tools: /bin/netstat
$ sudo apt reinstall coreutils e2fsprogs passwd procps systemd net-tools
......
dpkg: error processing archive /var/cache/apt/archives/coreutils_9.4-3ubuntu6.3_amd64.deb (--unpack):
 unable to make backup link of './usr/bin/dir' before installing new version: Operation not permitted
dpkg-deb: error: paste subprocess was killed by signal (Broken pipe)

什么情况，还不让重装了？这个“Operation not permitted”是什么？

$ sudo rm /usr/bin/dir
rm: cannot remove '/usr/bin/dir': Operation not permitted

删除也不让删？这应该不是权限问题，印象里好像在只读文件系统里操作的时候见过，这里应该不是吧，那还有什么？是不是和什么附加属性有关？什么attr？lsattr？

$ lsattr /usr/bin/dir
----ia--------e------- /usr/bin/dir
$ lsattr /usr/bin/cat
--------------e------- /usr/bin/cat

比正常的多了ia，查了一下好像确实和禁止写有关，但是也会影响删除吗？要怎么改，chattr？

$ sudo chattr -ia /usr/bin/dir
Usage: vmlinux1 [-pRVf] [-+=aAcCdDeijPsStTuF] [-v version] files...

这下终于看懂这个chattr是什么意思了。busybox能救吗？

$ sudo busybox chattr -ia /usr/bin/dir
chattr: applet not found

上网查了一下busybox是有chattr的，Ubuntu（或者应该怪Debian）给的居然没有编译进去，好在网上有预编译的完整版busybox-static。

$ wget https://github.com/EXALAB/Busybox-static/raw/refs/heads/main/busybox_x86
$ chmod a+x busybox_x86
$ sudo ./busybox_x86 chattr -ia /usr/bin/dir /usr/bin/ls /usr/bin/chattr /usr/bin/passwd /usr/bin/uptime /usr/bin/w /usr/bin/systemctl /bin/netstat
$ sudo apt reinstall coreutils e2fsprogs passwd procps systemd net-tools

确认一下是否清理干净：

$ sudo kill -9 443656
$ sudo rm /usr/bin/tmuxinfo3035aa41c1e9163b
$ sudo rm /usr/lib/systemd/system/tmuxinfo3035aa41.service
$ sudo debsums --changed
$ sudo mount
$ sudo systemctl
$ btop

看起来没有别的被改动的文件，负载也下来了，观察一天没有发现新的异常，基本确认处置完成。也许还有别的隐藏手段或其他病毒遗留，待之后见招拆招。
